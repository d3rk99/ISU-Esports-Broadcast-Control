# ISU Stream Server — scaffold handoff

## Scope and repository findings

This is a standalone Director PC Electron application. It never imports or launches the Broadcast Controller. All capture, encode, delay and output behavior is **simulation only**. There is no FFmpeg, DeckLink SDK, media queue, HTTP listener or RTMP connection. Do not use simulated READY as evidence of a league-compliant media delay.

The existing repository uses Electron main/preload CommonJS, vanilla JavaScript renderers, Node's test runner, Vite for the controller and electron-builder for separate executables. Existing bridge and stage-client packages demonstrate independent entry points. Configuration uses JSON under Electron userData; there is no common structured logging/credential facility suitable to import without coupling to controller services. This application follows those conventions, adds a small local JSONL logger and credential-store port, and uses static UI files instead of an unnecessary second Vite server. No existing runtime source, dependencies or controller build configuration were changed. Development tools are reused from the repository root node_modules.

## Build and run

From the repository root (Windows, Node/npm and installed root dependencies):

```powershell
npm install
npm --prefix stream-server start
npm --prefix stream-server test
npm --prefix stream-server run smoke
npm --prefix stream-server run build
npm --prefix stream-server run package
```

`build` produces `release/stream-server/win-unpacked/ISU Stream Server.exe`. Keep the whole win-unpacked folder together. `package` creates a portable Windows x64 executable in `release/stream-server`. These commands never build or run the controller. The existing root build/package targets remain unchanged. This app has no runtime npm dependencies. Its own package and builder manifest set a distinct identity, name, entry point and output directory. Electron 44.3.0 is pinned in the builder manifest because nested projects cannot resolve the parent's range during packaging; update it with the repository's installed Electron version when upgrading the shared toolchain. Electron's default icon is intentional for this scaffold.

Smoke mode launches actual Electron/Chromium with an isolated temporary userData directory. It verifies renderer initialization, blocked starts, form-driven settings saves, zero-delay connection transitions, stop behavior and restoring the five-minute interlock, then exits. It briefly shows the window without activating it to capture a current compositor frame and writes a screenshot to the printed temporary path. It sends no media. Unit tests cover service interlocks, reconnect cancellation, disabled outputs, delay values, persistence, private credentials and invalid config. There is no automatic resumption of streams after restart.

## State and command flow

The main process owns a single `StreamService`, one capture source, one encoder, one delay buffer and one output manager. The renderer calls `view()` for safe config/device/status DTOs and receives status events. All UI controls invoke `command(action, payload)`. Main serializes commands and clock ticks to avoid async lifecycle races. Readiness, commands and configuration are owned by the service, never inferred from DOM state.

Input reports connected/no signal with detected format; encoder reports READY/ENCODING; delay reports configured seconds, filled seconds, effective delay and ready. Output states are DISABLED, STOPPED, CONNECTING, CONNECTED, ERROR and RECONNECTING. Status also exposes uptime, bitrate, encoded/dropped frames, A/V warning and per-output reconnect counts. Telemetry is explicitly synthetic; frames stay at zero because no frames are produced.

At startup fake capture connects and the fake encoder starts; outputs remain stopped. Delay starts empty, defaults to 300 seconds and fills using elapsed monotonic time. Each timer step is capped at two seconds so suspension cannot instantly fill the buffer. Only the buffer clock accelerates at 30×/60×; uptime and reconnection use real elapsed time. Zero delay becomes ready on the first valid input tick. Config supports 0–86400 seconds (including 30, 60, 300, 600 and longer). Minutes in display may exceed 59.

Both individual and master starts check `input.connected && buffer.ready` in the output manager. Disabled destinations cannot start individually and are skipped by START ALL. Repeated starts are idempotent while connecting/connected. Simulated connect takes one second. Failure on a connected output enters ERROR, then RECONNECTING after one second, then CONNECTED after another second. Stop cancels that state machine immediately; ticking cannot resurrect a stopped destination. Reconnect counts last until settings are reapplied or the app restarts.

Signal loss, reset and successful settings application stop **all** outputs and invalidate buffer readiness. Signal restoration refills from zero. Every settings save, even just a destination name edit, intentionally resets the pipeline in this first scaffold. Invalid config is rejected before disturbing the running simulation. If a disk save fails after outputs were stopped, configuration remains unchanged and the error is shown; outputs stay stopped. Future async production stop/start failure rollback needs explicit lifecycle design.

Editing form fields does not mutate service state until SAVE SETTINGS; Start controls are disabled while edits are pending. Stop remains available. Status updates modify text/progress only, keeping typing and focus intact. Keys are password fields; blank retains an existing key and Clear saved key removes it. Add/remove supports any number of generic destinations, using stable IDs. Initial Twitch/YouTube/League entries are labels only, without platform-specific URLs or behavior. Empty URLs/keys are allowed only because this is simulation.

## Configuration and credentials

Normal runtime data is `%APPDATA%/ISU Stream Server/`, independent of all controller/bridge settings. `config.json` schema version 1 stores input/encoder selections, bitrates, format, delay and destination definitions. Temporary-file + rename saves avoid partial JSON writes. Unknown schema or corrupt JSON fails startup without replacing the original file. There are no migrations yet; add explicit version migrations later.

`ICredentialStore` is the replacement seam. `ElectronCredentialStore` uses Electron safeStorage (Windows DPAPI user-bound protection) to encrypt keys into base64 ciphertext in each destination's `credential` property. It refuses nonempty keys when encryption is unavailable; it never falls back to plaintext. Config returned over IPC excludes ciphertext and keys, exposing only `hasKey`. UI key values exist only during editing/IPC save and are cleared after successful saving. Credentials are not decrypted in simulation; future output adapters obtain them at connection time in the main process, not from status DTOs. Handle lost Windows credentials/decryption failure by requesting key re-entry. This is encryption at rest, not a portable secret backup or protection against software running as the same Windows user.

Server URL validation requires a matching RTMP/RTMPS scheme and hostname and rejects username/password/query/fragment. Operators must put keys in the key field, never in a server path. Future adapters must validate provider-specific URL path conventions and reject incomplete live destinations before connection. Do not serialize raw configuration, URL paths, credentials or FFmpeg stderr into logs.

## Logging

`logs/stream-server.jsonl` holds timestamped JSON events: application startup, device discovery, input/encoder/delay states, connection attempts, stream starts/stops, failures, reconnect attempts and command/tick failures. It rotates at approximately 5 MiB to one `.1` backup. Only state, numeric seconds/count, safe code and numeric destinationIndex are accepted. Destination index is one-based in the currently saved destination order; display names/URLs/IDs are not logged. This deliberately avoids user-controlled secret leakage. The active UI shows readable command errors. Corrupt-config startup displays a generic preservation notice. Review I/O failure handling and add an operator log viewer before production; logging is synchronous and should move off the media hot path.

## Future media engine: encode once

```text
ICaptureSource → IEncoder (one program instance) → IDelayBuffer
                                                    ↓ released encoded packets
                                           IStreamOutputManager
                                             ↙       ↓       ↘
                                    bounded queue per destination
                                             ↓       ↓       ↓
                                    IStreamMuxer / IStreamDestination
```

The contracts are JavaScript abstract base classes (methods throw until implemented). Simulation subclasses provide lifecycle/state behavior; `write`/`publish` deliberately produce no media. `IStreamMuxer` remains a port only. Implement new modules under `core/media/` (suggested) and select them at the composition/service boundary. Refactor `StreamService` construction for injected real adapters and event-driven progress when adding the engine: its `tick` method is explicitly a simulation driver and must never certify real readiness. Do not turn simulation into a hidden production fallback.

Recommended contract payloads for that next pass (not implemented):

- Capture `frame`: `{ kind: 'video'|'audio', pts, timeBase: {num,den}, duration, data, format }`; events `signal`, `frame`, `error`; discover/start/stop lifecycle. Define native frame handle ownership and release explicitly; avoid IPC copies.
- Encoder `packet`: immutable `{ kind, pts, dts, duration, timeBase, keyframe, codecConfig, data, epoch }`. Use integer/rational timestamps (BigInt where needed), one common program clock and explicit codec configuration/discontinuity events. Encoder consumes capture frames once; outputs must never construct encoders.
- Delay consumes encoded packets and emits `packet` only after real release eligibility, plus `status` with contiguous playable A/V duration, requested/effective delay and readiness. Reset invalidates prior-epoch packets and readiness; close releases storage and handles. Awaitable writes provide backpressure; no unbounded EventEmitter packet queues.
- Output manager receives released packets and feeds independently bounded output queues. Destinations own protocol connections and container/protocol muxers, not encoders. Muxing once per destination may be required; encoding once remains invariant. Slow/disconnected destinations must not block healthy destinations or grow memory indefinitely. Specify queue overflow/keyframe recovery before implementing.

### FFmpeg and DeckLink integration

Add FFmpeg process/native-library adapters behind these ports, with no renderer FFmpeg dependency. Decide subprocess versus native bindings and binary licensing/distribution explicitly; no binaries are downloaded by this scaffold. The existing Electron build downloads only its normal application runtime. Move heavy media work to a worker/utility process. Keep state/commands in the main service, and marshal telemetry rather than media through Electron IPC. Native DeckLink discovery/capture belongs behind ICaptureSource, with device capability negotiation; the UI must not depend on DeckLink classes. Support other capture adapters using the same frames/clock contract.

### Recommended true delay design

Prefer bounded rolling encoded segments on a dedicated local disk, plus a small RAM index/queue, rather than a five-minute raw-frame RAM buffer. At 12,000 kbps video + 192 kbps audio, 300 seconds is approximately 457 MB (decimal) before mux/index/headroom; 600 seconds doubles it. Preflight storage capacity and disk throughput. Segment on suitable keyframes while retaining codec headers, A/V timestamp continuity and enough history to start each destination cleanly. Use one timeline for both audio and video, preserve PTS/DTS ordering and account for capture/encoding/mux latency in measured end-to-end delay.

Readiness must prove contiguous decodable media for the requested interval, synchronized audio coverage and a valid release point. Elapsed wall time or a numeric percentage is insufficient. Increasing delay should lock/stop outputs and refill; define decrease behavior explicitly (initially stop/refill as scaffold does) so catch-up never leaks undelayed material. Input discontinuity, disk errors, missing audio/video, stale epochs and restart invalidate readiness. Never silently bypass the interlock or reconnect to live capture. Reconnect begins from the delayed timeline on a decodable keyframe with bounded queues; document whether additional latency is introduced. On shutdown, close output/capture/encoder/buffer resources in a defined order; on restart conservatively discard stale readiness. Implement bounded retention, crash recovery and disk cleanup before live use. RAM/segmented/other implementations fit IDelayBuffer without changing UI controls.

## Future Companion API

No network server is started. A future authenticated local HTTP/WebSocket adapter can map `GET /api/status` to `status()`, `POST /api/stream/start|stop` to startAll/stopAll, `POST /api/delay` to a validated service settings command, and `/api/outputs/{id}/start|stop` to individual commands. Reuse the serialized queue, service interlock and safe DTOs; do not reach into output objects from a route. Add authentication, origin/body-size checks, bind policy and status subscriptions when implementing it. The controller's existing API and ports remain unrelated.

## Remaining production work

Real capture, encode, clock synchronization, packet transport, muxing, storage/release validation and RTMP(S) streaming are all intentionally absent. Also pending: production dependency injection/lifecycle rollback, encoder errors and recovery, real telemetry and preview, adapter conformance tests, bounded backpressure, disk management, network retry/backoff, keyframe startup, live config validation, credential migration, config backup/migration, asynchronous logging/visible log health, operator log viewer, secure API and production packaging icon/signing. Do not claim this scaffold can stream or enforce a real broadcast delay until those are implemented and tested with hardware and destinations.
